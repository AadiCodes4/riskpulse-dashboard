# RiskPulse

RiskPulse is a small, independent, full-stack portfolio project: a real-time
**operations / risk monitoring dashboard**. Imagine a small business that
receives a stream of incoming records (purchases, orders, wire transfers,
loan applications, refund requests) and wants to auto-score each one for
risk and watch them come in live. RiskPulse implements exactly that, end to
end, with a working REST + WebSocket API, a real (if intentionally simple)
scoring engine, and a live-updating React dashboard.

> **This is a personal/portfolio project, built independently and from
> scratch.** It is **not affiliated with, derived from, or representative
> of any employer's systems, code, or data.** Every record in this repo's
> demo database is **synthetic, fabricated data** generated by
> [`backend/seed_and_simulate.py`](backend/seed_and_simulate.py) — no real
> people, accounts, or transactions are involved. The risk-scoring logic
> in [`backend/app/risk_engine.py`](backend/app/risk_engine.py) is a
> **simplified educational demonstration** (fixed category weights + a
> step-function on amount + a basic z-score anomaly check) — it is
> **not** a real financial risk model and should not be used to make any
> actual risk decisions.

## Tech stack

- **Backend**: Python, FastAPI, SQLAlchemy, SQLite (swap `DATABASE_URL`
  for Postgres/MySQL with no code changes), Pydantic v2, `pytest`.
- **Real-time**: a native WebSocket endpoint (`/ws`) that broadcasts every
  newly-created record to connected clients. The frontend also has a
  polling fallback (`GET /records` every few seconds) if the WebSocket
  connection drops, so the dashboard stays live either way.
- **Frontend**: React 18 loaded via CDN `<script>` tags with in-browser
  Babel — a single `index.html`, no `npm install` / build step required.
  The risk-score trend chart is a small hand-rolled inline SVG line
  chart (no charting library dependency).

## Data model

`Record` (table `records`):

| field         | type                                  | notes                                   |
|---------------|----------------------------------------|------------------------------------------|
| `id`          | string (uuid4 hex)                     | primary key                              |
| `submitted_at`| datetime (UTC)                         | indexed                                  |
| `category`    | enum (`retail_purchase`, `online_order`, `wire_transfer`, `subscription`, `loan_application`, `refund_request`) | indexed |
| `amount`      | float (≥ 0)                            |                                           |
| `applicant`   | string                                  | synthetic label, e.g. `demo-acct-4821`   |
| `risk_score`  | float 0–100                             | computed server-side on create           |
| `status`      | enum (`low`, `medium`, `high`, `critical`) | derived from `risk_score`             |
| `score_reason`| string                                  | short human-readable breakdown           |

## Risk scoring logic (`risk_engine.py`)

The final `risk_score` (clamped 0–100) is the sum of three independent,
individually-testable components:

1. **Category weight (0–35)** — a fixed weight per category (e.g. a wire
   transfer is treated as inherently riskier than a subscription renewal
   in this toy domain).
2. **Amount tier (0–45)** — a deterministic step function on `amount`
   (larger amounts score higher).
3. **Anomaly / z-score component (0–20)** — given a rolling window of the
   most recent amounts *in the same category*, computes how many standard
   deviations the new amount is from that recent mean. Values more than
   ~1 standard deviation out start contributing extra risk, capped at 20.
   With fewer than 3 recent samples for that category, this component is
   skipped (0).

`status` is then bucketed from the total score: `low` (0–25), `medium`
(26–50), `high` (51–75), `critical` (76–100).

This is a deliberately simple, fully-transparent scoring approach chosen
so it's easy to test and easy to explain — not a claim of real-world
predictive accuracy.

## Running the backend

Requires Python 3.10+.

```bash
cd backend
pip install -r requirements.txt          # or: pip install -r requirements.txt --break-system-packages
uvicorn app.main:app --reload --port 8000
```

The API is now live at `http://127.0.0.1:8000` (interactive docs at
`http://127.0.0.1:8000/docs`). On first run it creates `backend/riskpulse.db`
(SQLite) automatically.

### Seeding historical data + simulating a live stream

With the server running (in another terminal):

```bash
cd backend
python3 seed_and_simulate.py --seed-count 150 --days-back 7 --stream-count 30 --interval 1.0
```

- **Seed phase**: writes `--seed-count` synthetic historical records
  directly into the database, with timestamps spread over the last
  `--days-back` days (default profile of "typical" amounts per category —
  entirely made up for this demo, see `CATEGORY_AMOUNT_PROFILE` in the
  script).
- **Simulate phase**: POSTs `--stream-count` new synthetic records to the
  *running* API, one every `--interval` seconds, so a connected dashboard
  sees them arrive live over the WebSocket. A small fraction of records
  (`ANOMALY_SPIKE_PROBABILITY`, default 6%) are deliberately generated as
  outliers so the anomaly-detection component of the risk engine has
  something to catch — these are tagged `<-- SPIKE` in the script's
  console output.

Run `python3 seed_and_simulate.py --help` for all options (you can seed
only, stream only, point at a non-default API URL, etc).

### Running the tests

```bash
cd backend
python3 -m pytest tests/ -v
```

## Running the frontend

The frontend is a single static HTML file with no build step. Two ways to
run it:

1. **Open directly**: just open `frontend/index.html` in a browser. It
   talks to `http://127.0.0.1:8000` by default.
2. **Serve it** (recommended, avoids `file://` CORS quirks in some
   browsers):
   ```bash
   cd frontend
   python3 -m http.server 5173
   # then open http://127.0.0.1:5173
   ```

If your backend runs somewhere other than `127.0.0.1:8000`, set
`window.RISKPULSE_API_BASE` before the app script runs, e.g. by adding
`<script>window.RISKPULSE_API_BASE = "http://your-host:8000";</script>`
above the main app `<script>` tag in `index.html`.

The dashboard shows a connection badge (Live via WebSocket / Polling
fallback / Disconnected), a summary panel, a status breakdown, a
per-category breakdown, an inline SVG chart of recent risk scores, and a
filterable live feed table.

## Running everything with Docker

```bash
docker compose up --build
```

This builds and runs the FastAPI backend on `http://localhost:8000` with
its SQLite data persisted in a named Docker volume. The frontend isn't
containerized (no build step needed) — serve it separately as shown
above, e.g. `python3 -m http.server 5173 --directory frontend`.

## REST API reference

| Method | Path             | Description                                          |
|--------|------------------|-------------------------------------------------------|
| GET    | `/health`        | liveness check                                        |
| POST   | `/records`       | create + auto-score a new record                      |
| GET    | `/records`       | list/filter records (`category`, `status`, `min_risk`, `max_risk`, `limit`, `offset`) |
| GET    | `/records/{id}`  | fetch a single record                                  |
| GET    | `/stats`         | aggregate counts, avg risk, status breakdown, per-category stats |
| WS     | `/ws`            | live broadcast of every newly-created record           |

Example:

```bash
curl -X POST http://127.0.0.1:8000/records \
  -H "Content-Type: application/json" \
  -d '{"category": "wire_transfer", "amount": 30000, "applicant": "demo-acct-1"}'
```

## Known limitations / possible extensions

- SQLite is used for simplicity; the code is written against portable
  SQLAlchemy so switching `DATABASE_URL` to Postgres/MySQL should work
  without other changes, but this hasn't been tested against them.
- The risk engine is intentionally simple (see disclaimer above) — a
  natural extension would be a real ML model trained on labeled outcomes,
  proper probability calibration, and interaction effects between
  features instead of three independently-summed components.
- The WebSocket broadcast is in-process only (a single `ConnectionManager`
  in memory) — running multiple backend replicas behind a load balancer
  would need a shared pub/sub layer (e.g. Redis) to fan out broadcasts
  across processes.
- No authentication/authorization — this is a local demo, not a
  production-ready service.
